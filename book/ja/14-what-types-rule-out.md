# 14. 型が排除するもの

第 I 部と第 II 部を通じて、各章でエラー、エフェクト、`Immediate`、ケイパビリティ、`match` を個別に見てきました。これらはすべて 1 つの型・エフェクトシステムを構成しています（`[type]`）。この章ではそれらを並べて整理し、プログラムの実行前にコンパイラが検査して保証する事柄をまとめます。

## すべての式は 3 つの要素を持つ：`T`、`E`、`R`

型検査はすべての式に次の 3 つ組を割り当てます（`[type.judgment]`）。

```text
T ! E ; R
```

- `T` は値の型で、Hindley-Milner 流に推論されます。`Never` は分岐の合流点（`if`、`match`、`escape`）や期待型のある位置で任意の型と合流するため、`fail` や `panic` はどこにでも収まります。一方、型引数の中では `List[Never]` と `List[Int]` は別の型のままです（`[type.rules]`）。
- `E` は、その式が `fail` で発生させ得るエラータグの集合です。空であれば、その式は型付きエラーで失敗しません。
- `R` は、その式が必要とするエフェクト、ラベル、ケイパビリティの集合です。空であれば、その式は環境に依存しません。

`E` と `R` の両方が空である関数を*純粋*（pure）と呼びます。

関数のシグネチャにどこまで書くかによって、何が推論され何が強制されるかが決まります（`[type.inference]`）。

| 要素 | 省略したとき | 書いたとき |
|---|---|---|
| 戻り値の型 `-> T` | `T` と `E` が推論される | `T` が検査され、`E` は `fails` の範囲内に収まる必要がある |
| `fails` 節 | `-> T` を書いていれば空（エラーなし） | 関数のエラーをその集合に固定する（本体のエラーはその範囲内に収まる必要がある） |
| `uses` 節 | `R` は常に推論される（`-> T` を書いていても） | 関数のエフェクトをその集合に固定する（本体のエフェクトはその範囲内に収まる必要がある） |

`fails` や `uses` を書いた場合でも、パラメータとして受け取る関数の隠れたエラー集合・エフェクト集合や、ケイパビリティパラメータのケイパビリティ集合は、書いた集合と並んで自動的に運ばれます。`fails` なしで `-> User` と書けば、発生し得るすべてのエラーをその関数内で処理していることが保証されます。`uses { Console }` と書けば、それ以外のエフェクトを使わないことが保証されます。`main`、テスト、`@export` 関数では、エントリが提供するホストエフェクトを除いて `R` は空でなければならないため（`[effect.with]`、`[effect.host]`）、実行時に必要なハンドラが欠けているという事態は決して起きません。

## 関数型と集合型パラメータ

関数型 `fn(A) -> B fails E uses { R }` において、`fails` や `uses` を省略したときの意味は、その型を*どこに*書いたかによって決まります（`[type.fn]`）。

| 位置 | 省略したときの意味 |
|---|---|
| パラメータの型の内側（`f: fn(A) -> B`、`fs: List[fn(A) -> B]`） | 任意のエラーやエフェクト（呼び出し側へ伝播する隠れた集合変数） |
| 戻り値の型、束縛の型注釈、無名関数のパラメータ | 本体から推論される |
| 宣言の内側（`type`、`enum`、`error`、`handler`、`effect`、`trait`、`const`） | 空（純粋） |

この使い分けのおかげで、`List.map` のような高階関数は余計な構文なしで純粋なコールバックもエフェクトを持つコールバックも受け入れられ、一方でデータ構造やエフェクト操作がエフェクトを密かに抱え込むことは防がれます。エフェクトを持つ関数を `type` に格納したい場合は、そのエラー集合とエフェクト集合を型パラメータとして公開します。

```emel
import Std.Console.{Console, SystemConsole}

error BadInput derive Show

type Endpoint[E, R](handle: fn(String) -> String fails E uses { R })

fn run_endpoint[E, R](ep: Endpoint[E, R], input: String) -> String fails E uses { R } {
  f = ep.handle
  f(input)
}

fn pure_echo(s: String) -> String {
  "echo: #{s}"
}

fn logged_echo(s: String) -> String fails BadInput uses { Console } {
  if s == "" { fail BadInput }
  console <- Console
  console.print_line("received #{s}")
  s
}

fn main() {
  with SystemConsole {
    endpoints: List[Endpoint[BadInput, Console]] = [
      Endpoint(handle: pure_echo),
      Endpoint(handle: logged_echo),
    ]
    out = List.map(endpoints, |ep| run_endpoint(ep, "hi"))
    dbg(out)
    ()
  }
}
```

```console
$ emela run
received hi
["echo: hi", "hi"]
```

型パラメータが通常の型、エラー集合、エフェクト集合のどれを表すかは使われ方（`fails E`、`uses { R }`）から推論されるため、カインド構文は不要です。集合型引数に複数の要素を書くときは `fails` や `uses` と同じ記法を使い（`Endpoint[BadInput | Timeout, { Console, Clock }]`）、空集合は `{}` と書きます。

### ジェネリック関数で集合から差し引く

`escape` も `with` も、自身が処理・提供した要素を `E` や `R` から差し引きますが、*不透明な*集合変数から差し引くことはできません（`[error.escape]`、`[effect.with]`）。`fn run(f: fn() -> ()) { with ConsoleLogger { f() } }` では、内側で `ConsoleLogger` を提供しているにもかかわらず、`f` の隠れたエフェクト集合は `run` の `R` にそのまま残ります。

型の上でも特定のエラーやエフェクトを取り除くには、集合型パラメータの隣にその名前を並べて変数の外に出します。

```emel
fn run[R](f: fn() -> () uses { Logger, R }) -> () uses { R } {
  with ConsoleLogger { f() }
}
```

## `E` と `R` の包含関係

先ほどの `Endpoint` の例では、空の `E` と `R` を持つ `pure_echo` が `logged_echo` と一緒に `Endpoint[BadInput, Console]` へ入っています。これが成り立つのは*包含関係*（containment）があるからです（`[type.rules]`）。

- より小さな `E` や `R` を持つ関数は、より大きな `E` や `R` が期待されるどの場所にも使えます。純粋な関数はどのエラー集合・エフェクト集合にも収まります。
- 異なる `E` や `R` を持つ関数が `if` や `match` の分岐やリストの要素として合流するとき、それらの `E` と `R` は和集合でまとめられます。
- 関数型のパラメータ位置の内側では、包含関係の向きが逆転します。`Console` を使うコールバックを受け取れるランナー（`fn(fn() -> Int uses { Console }) -> Int`）は、純粋なコールバックだけを受け取るランナー（`fn(fn() -> Int uses {}) -> Int`）が期待される場所へ渡せます。期待された型を通じてそれを呼ぶ側が渡せるのは純粋なコールバックだけであり、そのランナーはそれをすでに受け入れられるからです。
- 名前付き型の型引数（`Endpoint[E, R]`）の内側では、集合は一致によって照合されます。`Endpoint[{}, {}]` と `Endpoint[BadInput, Console]` は別の型です。一方、`Endpoint(handle: pure_echo)` が通るのは、`pure_echo` 自身が期待される関数型 `fn(String) -> String fails BadInput uses { Console }` に対して検査されるためです。

`E` と `R` の包含関係は、Emela における唯一の部分型付け（サブタイピング）です（`[type.not]`）。値の型自体に部分型付けはありません。

## `Immediate`：意図しない中断を排除する

第 12 章で見たとおり、`R: Immediate` は式が中断せずにその場で完了することを保証します（`[type.effect-bound]`）。

- `effect` のすべての `fn` 操作（および非 `suspend` のハンドラメンバ）が検査されるため、呼び出し側はどのハンドラが組み込まれていてもその呼び出しが決して中断しないことを信頼できます。
- `@external` 関数に渡すコールバックはデフォルトで `Immediate` になり（明示的に書いた `uses` 節も `Immediate` でなければならない）、同期的に返ることを期待するホストコードへ中断するコールバックが渡ることは決してありません。
- `Immediate` は `R` に含まれるエフェクトから計算され、その場で再開するハンドラは `Async` を加えずに自身のエフェクトを取り除くため、関数を重複して書かずに同じジェネリックコードを中断する文脈でも中断しない文脈でも使えます。

## 漏洩できないケイパビリティ

ケイパビリティ（`use E`）とケイパビリティ束縛型（`type Handle uses Files`、`Task[A] uses TaskGroup`）は、型の中に隠れたケイパビリティ集合を運んでいます（`[type.rules]`、`[effect.escape]`）。

- ケイパビリティの操作を呼ぶと、`R` に加わるのはエフェクト名 `E` ではなく*そのケイパビリティ自身*です。ケイパビリティがエフェクト名へ広げられることはないため、`R` からそれを取り除けるのはそれを作った特定の `with` だけです。
- ケイパビリティ、`Task[A]` のようなケイパビリティ束縛値、それらをキャプチャしたクロージャ、あるいはフィールドにそれらを保持するエラーを、その `with` の外へ返したり送出したりするコードはコンパイルできません。

```emel
import Std.Task.{Task}

fn leak_task() {
  with tasks = Task.Group {
    tasks.start(|| 1)
  }
}
```

```console
$ emela check
error[E4405]: capability `tasks` leaves the `with` that made it
   ╭─[ src/main.emel:5:5 ]
   │
 4 │   with tasks = Task.Group {
   │                ─────┬────
   │                     ╰────── made here; it ends with this `with`
 5 │     tasks.start(|| 1)
   │     ────────┬────────
   │             ╰──────────
───╯

1 error
```

- ケイパビリティを外側の `State` に格納しようとしたり、外側のハンドラ操作に渡そうとしたりしても、外側の型は内側の `with` が存在する前に確定しているため型検査で弾かれます。
- ケイパビリティパラメータを持つ関数型（`fn(use ReadFile) -> String`）は未知のケイパビリティ集合について全称量化されるため、そこへ渡されたクロージャは実行中にケイパビリティの操作を呼び出すことはできても、それを返したり外へ持ち出したりすることはできません。

`init` と `release`（第 11 章）と合わせることで、これらのルールはクローズ後の使用（use-after-close）バグをコンパイル時に根絶します。

## 網羅性と反駁可能性

すべての `match` は、対象となる値が取り得るすべてのケースを覆わなければなりません（`[fn.match]`）。

```emel
enum Status {
  Pending
  Running(worker: Int)
  Done(code: Int)
}

fn label(s: Status) -> String {
  s match {
    Pending             -> "pending"
    Running(w) if w > 0 -> "running"
    Done(code:)         -> "done (#{code})"
  }
}
```

```console
$ emela check
error[E3102]: non-exhaustive match: pattern `Running(_)` not covered
   ╭─[ src/main.emel:8:3 ]
   │
 8 │   s match {
   │   ┬
   │   ╰──
───╯

1 error
```

- コンパイラは任意の条件式を評価しないため、ガード（`if w > 0`）の付いたアームは網羅性に数えられません。
- `enum` にバリアントを追加すると、ワイルドカードのないすべての `match` が新しいケースを処理するまでコンパイルエラーになります。
- それより前のガードなしアームですでに覆われている冗長なアームには警告が出ます。
- `Never` に対する `match` であっても少なくとも 1 つのアームが必要です（空の `match {}` はコンパイルできません）。
- 束縛（`x = ...`）が受け入れるのは反駁不能（irrefutable）なパターンだけです。`Some(x) = opt` のような反駁可能なパターンはコンパイルできません。
- 一方で `escape` には網羅性は求められ*ません*（`[error.escape]`）。エラータグが `E` から取り除かれるのは、そのエラーに対するガードなしアームがすべての値を覆うとき（`NotFound(_)`）だけです。部分的なパターン（`NotFound(id: 1)`）やガード付きアームではそのタグが `E` に残り、マッチしなかったエラーは呼び出し元へ伝播します。

## 型システムに含めないもの

上記の保証が予測可能に保たれているのは、Emela が意図的に含めない選択をしているものがあるからです（`[type.not]`）。

- 一般的な部分型付けはありません（`E` と `R` の包含関係のみ）。
- 一般的な合併型や交差型はありません（合併はエラー集合 `E` にのみ、ケイパビリティの組み合わせは `use E1 + E2` にのみ現れます）。
- 高カインド型、行多相（フィールドアクセスやメソッド呼び出しには既知の名前付き型が必要）、多相再帰はありません。
- null、暗黙の型変換、動的型付けはありません。

## まとめ

- すべての式は 3 つ組 `(T, E, R)`（値の型、エラー集合、エフェクト集合）を持ちます。すべてのエラーは処理されるか `fails` に宣言されなければならず、すべてのエフェクトは `main` かテストで提供されなければなりません。
- 省略された `fails` と `uses` は、関数のパラメータでは多相になり、戻り値の型や束縛では推論され、宣言の内側では空になります。
- 包含関係により、より小さな `E` や `R` を持つ関数をより大きな集合が期待される場所で使え、関数のパラメータ内では向きが逆転します。値の型に対する一般的な部分型付けはありません。
- `Immediate` は、中断しない操作やホストコールバックに中断し得るコードが入り込むのを防ぎます。
- ケイパビリティ追跡により、ケイパビリティ（`use E`）もケイパビリティ束縛値（`Task[A]`）も自分の `with` より長く生きられません。
- 網羅的な `match`、反駁不能な束縛、`escape` での正確なエラー差し引きにより、未処理のケースが黙ってすり抜けることはありません。

## 第 II 部の終わり

第 II 部では言語の基盤を扱いました。トレイトと `derive`、独自のエフェクト・ハンドラ・レイヤ・ラベルの定義、`init` と `release` による確定的なリソース解放、中断と構造化並行性、合成によるプログラム設計、そして型・エフェクトシステムがもたらす保証です。

第 III 部ではホストとターゲットとの境界を越えます。同じプログラムが JavaScript、WebAssembly、C の上でどのように動作するか、`@external` と `@export` が Emela とホストコードをどう橋渡しするか、そして現在のコンパイラがこれらの機能をどう実装しているかを見ていきます。第 15 章は 3 つのターゲットから始まります。
